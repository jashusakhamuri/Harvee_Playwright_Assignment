# Harvee QA Automation Assessment

A UI automation framework built with **Playwright and TypeScript** to test the SauceDemo application. The assessment deliverables cover manual test design, UI automation, reusable Page Object Model (POM) classes, centralized configuration, test data, execution reporting, and written responses for the assessment tasks.

## 1. Tech Stack

- **Playwright Test** — browser automation, test execution, and assertions
- **TypeScript** — test implementation
- **Page Object Model (POM)** — reusable page classes, locators, and page actions
- **Properties files** — application URL and demo-user credentials
- **JSON** — checkout test data and missing-field scenarios
- **Winston** — execution logging
- **Playwright HTML Reporter** — test execution results and failure details

## 5. Configuration

This project uses `.properties` files rather than `.env` files.

### Application URL

File: `src/config/environment.properties`

```properties
qa.url=https://www.saucedemo.com
```

### Demo-user credentials

File: `src/config/users.properties`

```properties
standard.username=standard_user
standard.password=secret_sauce

lockedOut.username=locked_out_user
lockedOut.password=secret_sauce

problem.username=problem_user
problem.password=secret_sauce

performanceGlitch.username=performance_glitch_user
performanceGlitch.password=secret_sauce
```

These are public SauceDemo demo credentials. Do not store real production credentials in source control.

The `propertiesLoader.ts` module loads the configuration, and `testFixtures.ts` makes the configuration available to tests. Tests should use the shared fixture and page objects to avoid duplicating configuration and page interactions.

## 6. Running Tests

Run all commands from the project root.

### Run the complete suite in Chromium

Recommended baseline command:

```powershell
npx playwright test tests --project=chromium --workers=1
```

Using one worker runs tests serially, which can be useful when investigating timing or shared-state issues. It does not, by itself, prove that tests are independent.

### Run a specific browser project

```powershell
# Chromium
npx playwright test tests --project=chromium --workers=1

# Firefox
npx playwright test tests --project=firefox --workers=1

# WebKit
npx playwright test tests --project=webkit --workers=1
```

Run all configured browser projects:

```powershell
npx playwright test tests --workers=1
```

Use the all-browser command only if Firefox and WebKit are configured in `playwright.config.ts` and their browser binaries are installed.

### Run a specific test file

```powershell
# Login
npx playwright test tests/login.spec.ts --project=chromium --workers=1

# Products and sorting
npx playwright test tests/products.spec.ts --project=chromium --workers=1

# Cart
npx playwright test tests/cart.spec.ts --project=chromium --workers=1

# Checkout
npx playwright test tests/checkout.spec.ts --project=chromium --workers=1

# B1: checkout total calculation
npx playwright test tests/B1_cart_total.spec.ts --project=chromium --workers=1
```

### Run a test by title

Use a substring from the test title. For example, if the title contains `TC17`:

```powershell
npx playwright test -g "TC17" --project=chromium --workers=1
```

The filter must match an actual test title. Check current titles before relying on a manual-to-automation mapping.

### Run with a visible browser

```powershell
npx playwright test tests --project=chromium --headed --workers=1
```

### List tests without executing them

```powershell
npx playwright test --list
```

### Display Playwright command options

```powershell
npx playwright test --help
```

## 7. HTML Execution Report

The project uses Playwright's HTML reporter.

### Generate the report

Run the suite you want represented in the report:

```powershell
npx playwright test tests --project=chromium --workers=1
```

### Open the report

```powershell
npx playwright show-report
```

The default report location is:

```text
playwright-report/index.html
```

The report contains execution results and available failure details or artifacts.

### Copy the report into `ExecutionReport/`

After the final run, execute these PowerShell commands from the project root:

```powershell
New-Item -ItemType Directory -Force -Path "ExecutionReport" | Out-Null

Copy-Item -Path "playwright-report\*" `
  -Destination "ExecutionReport" `
  -Recurse -Force
```

Copy the **entire report contents**, not just `index.html`, so supporting assets are retained. Repeat this after the final test run to keep the submission report current.

### Package the report

1. Open the project folder in File Explorer.
2. Right-click `ExecutionReport`.
3. Select the option to compress the folder to a ZIP file.
4. Submit the ZIP only if the assessment instructions allow it.

## 8. Test Coverage and Assessment Work Completed

The manual test suite is documented in `Docs/A1_Manual_Test_Cases.md`. The manual test IDs are `TC01`–`TC25`. Automated coverage must be checked against the actual test titles in `tests/` and the latest Playwright report.

### Manual test suite

| Area | Coverage |
|---|---|
| Login | Standard login, incorrect password, locked-out user, empty credentials, and missing password |
| Products | Product listing and all four sorting orders: name A–Z, name Z–A, price low–high, and price high–low |
| Cart | Add/remove products, cart badge, cart contents, cart navigation/state, and displayed prices |
| Checkout | Valid checkout details, subtotal/tax/total, missing required fields, order completion, cancellation, and cart state after completion |
| Security | Direct access to the Products URL after logout |
| Exploratory testing | A 15-minute exploratory charter using `problem_user` |
| Accessibility and responsive UI | Keyboard accessibility checks and a 375 × 667 viewport check |

The manual test document also includes product-owner questions and assumptions. Refer to that document for detailed steps, expected results, and assumptions.

### Automated test files

| Test file | Intended coverage |
|---|---|
| `tests/login.spec.ts` | Login behavior, including standard and locked-out-user scenarios. Check the file for the exact cases currently automated. |
| `tests/products.spec.ts` | Product listing, sorting, and product/cart interactions. |
| `tests/cart.spec.ts` | Adding/removing items, cart badge, and cart contents. |
| `tests/checkout.spec.ts` | Checkout workflows and required-field validation. |
| `tests/B1_cart_total.spec.ts` | B1 rewrite: checkout amount calculation, order confirmation, and cart state after completion. |

### B1 checkout-total test

The B1 test was run successfully in Chromium in the recorded execution. The observed amounts were:

- Subtotal: **$29.99**
- Tax: **$2.40**
- Total: **$32.39**

The test checked that the total equals subtotal plus tax, completed the order, verified the confirmation, and returned to the Products page to check the cart badge. This records the result of that specific run; it does not guarantee that future runs or other browsers will pass.

### Manual-to-automation traceability

The manual test document uses `TC01`–`TC25`. Automated test titles should use the matching manual ID for each automated case. Do not assume titles such as `TC1.1`, `TC2.2`, `TC3.1`, or `TC4.4` map to `TC01`–`TC25` unless the mapping is explicitly documented and accurate.

Before submitting:

1. Compare every automated test title with its corresponding manual test case.
2. Use consistent IDs in the manual suite, automated titles, and README.
3. Label cases as **manual only** when no corresponding automated test exists.
4. Use the Playwright report to confirm which tests actually ran and passed.

### Manual-only or not demonstrated as automated

Keyboard accessibility, responsive layout, the exploratory charter, and product-owner questions are documented assessment activities. Do not describe them as automated unless the submitted code contains corresponding automated checks. The UI suite also does not, by itself, demonstrate API or unit-test coverage.

## 9. Framework Design

### Page Object Model

Page classes encapsulate locators and page actions. Test files should describe the scenario and assertions while reusing page objects for page interactions.

### Shared fixtures

`src/fixtures/testFixtures.ts` loads configuration and provides shared test setup. Import the project fixture from test files that need the configured URL and user credentials.

### Centralized configuration

The application URL and demo-user credentials are stored in:

- `src/config/environment.properties`
- `src/config/users.properties`

### Test data

Checkout input values and missing-field scenarios are stored in:

```text
src/testData/checkoutData.json
```

### Logging

Winston records execution activity and useful debugging information. Credentials should not be written to logs.

### Failure artifacts

Screenshot and video capture are controlled by `playwright.config.ts`. Check that file to confirm which artifacts are captured and under what conditions.

## 10. Troubleshooting

### Browser binaries are missing

```powershell
npx playwright install
```

### A test fails

1. Read the terminal error and identify the failed assertion or action.
2. Open the HTML report:

   ```powershell
   npx playwright show-report
   ```

3. Inspect the failed test's error details and any available screenshots, videos, or error context under `test-results/`.
4. Review the Winston logs in `logs/`, if generated.
5. Re-run the affected test by itself, then run the full suite again.

### Tests appear unstable in parallel

Try a serial Chromium run while investigating:

```powershell
npx playwright test tests --project=chromium --workers=1
```

A serial pass does not prove that a test is parallel-safe or that a suspected issue is fixed. Investigate shared state, timing, and test independence before drawing that conclusion.

### Browser coverage

A passing Chromium run does not prove that Firefox or WebKit passes. Run each configured browser project and report its results accurately.

## 13. Scaling the Framework to 200 Tests

To scale the suite, keep tests independent, continue using page objects and shared fixtures, and store reusable test data in structured files. Use consistent test IDs for traceability. Add API tests where APIs are available and unit tests at the appropriate code layer. Integrate the suite into CI with clear reports and failure artifacts. Use tags or projects to separate smoke, regression, and browser-specific runs. Track flaky tests and investigate their root causes instead of relying on retries alone.
